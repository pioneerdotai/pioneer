# Соединение с LiveKit

После перехода в звонок клиент выполняет действие `Connect` метода `thread/call`
для нужного `call_id`. Клиент передаёт `credentials.url` и
`credentials.token` в штатный LiveKit SDK как есть. URL может содержать
настроенный префикс Gateway. SDK самостоятельно добавляет `/rtc` или
`/rtc/v1` и соответствующий `/validate`. Новый `Connect` выдаёт свежий
токен для действующей сессии участника. `expires_at_unix` относится к
выданному этим RPC токену.

При `gateway.calls.relay_media = true` Gateway берёт URL из действующего
Remote Access туннеля, меняет схему HTTPS на WSS и убирает конечный слеш
непустого префикса перед добавлением пути SDK. Для
этого режима `gateway.calls.signaling_url` и `livekit_node_ip` оставляют
пустыми. Relay должен иметь настроенные `media_bind_addr` и
`media_public_addr`. Публичный сетевой вход для клиента состоит из HTTPS/WSS
Gateway и общего IPv4 UDP-входа Relay. Клиентский токен действителен в
Gateway. Gateway обменивает его на отдельный локальный токен LiveKit и
переподписывает обновления токена из сигнализации. Для релейного режима
предложения и ответы LiveKit должны содержать сессионный `a=ice-lite`.
Если параметры подключения отключают ICE Lite, Gateway закрывает
сигнализацию до регистрации маршрутов и отправки такого SDP клиенту.

Gateway держит медиаканал на время соответствующего WebSocket. Закрытие
WebSocket освобождает ICE-маршруты, и новое подключение должно получить
SDP с зарегистрированными ICE-фрагментами. При потере медиаканала SDK
может возобновить разговор полным переподключением к той же комнате
через свежий `Connect`. Восстановление публикаций и использование
SDK resume поверх смены сети относятся к этапу 5.
